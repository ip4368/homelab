# Homelab Cluster Manager — Real K3s and Longhorn on the VM Lab

Date: 2026-10-27
Status: Built and validated on the VM lab (see §9). The storage network on VLAN 20 and replacing a dead K3s server were added on 2026-10-28 (§10).
Builds on: `2026-10-26-real-vm-lab-design.md` (the VM lab, phases A–D done) and the prototype design §11 (path to production).

## 1. Intent

The VM lab proved that homelabd's control plane works on real machines: join, approval, network templates, leader election and the VIP, switch observation, faults. The workload side was never real: the lab design's phase E (stand-in instances and replica files) was not built. This phase replaces it with **the real thing**:

- homelabd installs and joins **K3s** on every host once the host is `Ready` on its final network. Control-plane hosts run K3s servers with embedded etcd. Every other host runs a K3s agent.
- **Longhorn** runs on the K3s cluster and uses the data disks of the hosts that have the `storage` role.
- The lab installs machines **the way a person would**. It boots a plain Debian, logs in over SSH and runs the documented install commands. Nothing about homelabd is baked into the image.

The end-to-end run validates the whole stack the way it would run at home: real pods with real Longhorn volumes survive real power cuts.

## 2. Decisions

| Question | Decision | Why |
|---|---|---|
| Who runs workloads | **K3s and Longhorn.** On real hosts, homelabd's scheduler, failover and storage controllers stay idle. They remain sim-only stand-ins, covered by the sim tests. | That is the production path (prototype §11): configure and observe the real systems, do not reimplement them. |
| Who decides what a host runs of K3s | **The control plane.** A new leader-only `kube` controller sends each `Ready` host a `KubeSpec`: server or agent, init or join, node IP, labels and Longhorn disks. The agent applies it through `HostOs::apply_kube` and reports `KubeStatus`. | It keeps the anti-goal "no second code path": the sim runs the same controller against a stand-in `HostOs`. |
| K3s servers | **Hosts with the `ControlPlane` role**, which follows the homelabd Raft voters. A control-plane-eligible host gets no K3s while the voters are below target, because it may become a voter. Once the voters reach target it becomes an agent. A changed role is applied by uninstalling and reinstalling. | The VIP is held by the homelabd leader, so the leader's host must run a K3s API server. |
| K3s API endpoint | **The homelabd VIP**: `https://<vip>:6443`. Servers add `--tls-san <vip>`. Joining servers and agents register through it. | It is the fixed registration address K3s HA needs, and we already run one. The K3s agent then load-balances to every server by itself. |
| First K3s server | The host the cluster was bootstrapped on. The state records it (`KubeCluster.init_host`). It runs `--cluster-init`. Everyone else joins. | It is the only host when the cluster is created. |
| K3s token | Generated by `homelabd init`, kept in the Raft state and sent in each `KubeSpec`. | One secret per cluster, like `k3s --token`. It travels unencrypted, like every homelabd message (mTLS remains a non-goal). |
| Node network | `--node-ip` = the host's static mgmt address from IPAM. Flannel runs over the mgmt interface. K3s is installed only after the network config is confirmed, so the node IP never changes. | etcd peer URLs and node IPs must not change after install. |
| Longhorn install | A K3s `HelmChart` manifest (chart repo `charts.longhorn.io`, pinned version) written by every K3s server into `/var/lib/rancher/k3s/server/manifests/`. | It uses K3s's own addon mechanism and is idempotent. |
| Longhorn disks | Storage hosts annotate and label their own node: `node.longhorn.io/default-disks-config` listing `/mnt/<disk>` for each data disk, then `node.longhorn.io/create-default-disk=config`. Longhorn runs with `createDefaultDiskLabeledNodes`. A host that stops storing (its storage role held or removed) drops the label, and a running K3s server sets its Longhorn disks to `allowScheduling: false`, noting them in the Longhorn node's `homelab.io/storage-off` annotation so they are given back when it stores again. | Only storage-role hosts store data, and only on their data disks. Longhorn creates default disks only once, so taking them back needs Longhorn's own node object, which only a server's admin credentials can write. |
| Longhorn on node loss | `nodeDownPodDeletionPolicy: delete-both-statefulset-and-deployment-pod`. | A pod with a volume on a dead node restarts elsewhere instead of hanging in `Terminating`. |
| Storage network | **VLAN 20, through Multus** (rke2-multus thin plugin with whereabouts, and its CRD chart, both K3s `HelmChart`s written by every server). One `NetworkAttachmentDefinition`, `longhorn-system/homelab-storage`, has **no config**: Multus then reads `/etc/cni/multus/net.d/homelab-storage.conf` on each host, which homelabd writes as a macvlan on that host's own storage interface (`bond0.20`, `eth0.20`…). Pods take addresses (whereabouts) from the storage network's first reserved range, which the seed network sets to `10.20.3.0/24`. Longhorn's `storageNetwork` names the attachment. Longhorn's manager and instance managers run only on nodes labelled `homelab.io/storage-network=true`, set on hosts with a storage address. Without a reserved range, Longhorn stays on the pod network. | One cluster-wide definition, yet each host attaches to its own interface, whatever its name. A held host keeps its attachment (its VLAN 20 interface exists), so Longhorn's pods still start there. The reserved range keeps IPAM from giving those addresses to hosts. |
| Replacing a dead K3s server | **etcd's order: remove the dead member, then add the new one.** Servers report etcd's members (`/db/info`, which K3s answers on loopback for the admin) in `KubeStatus`. Once the dead host is no longer a Raft voter, the kube controller sends `Msg::KubeAdmin` to the first running server, which deletes the dead host's node. K3s's etcd controller then removes the member. The replacement gets its server spec only after that. Removal is one member at a time, only while the members on running servers are a quorum, and the server refuses to delete a node that is `Ready`. A member with no node to delete, or one that never started (no name; servers report it by peer address, its host's mgmt address), the server removes through etcd's gRPC API on loopback (`Cluster.MemberRemove`, sent with curl), then checks etcd no longer lists it. A server that cannot read `/db/info` reports why (`KubeStatus.etcd_unread`); while none can, nothing is removed and no server joins. | A new member added while a dead one still counts raises etcd's quorum with nothing to meet it. The leader's view of "down" comes from homelabd heartbeats; the node's `Ready` is Kubernetes' own, so both must agree before a member goes. |
| Versions | K3s `v1.36.5+k3s1` (stable channel), Longhorn `1.13.0` (needs Kubernetes ≥ 1.34). | Current stable releases, pinned so a lab run is repeatable. |
| How a machine is installed | **`install.sh`** (served next to the `homelabd` binary): `init` on the first machine, `join <vip> <token>` on the others, `upgrade` to replace the binary. The lab's "technician" runs these over SSH on a plain Debian 13 machine. | This is exactly what a person does at home. |
| Node config | `/etc/homelab/node.json` is `{host, vip, token}`. The host defaults to the hostname. The mgmt prefix is taken from the interface that holds the VIP's subnet. Switch management addresses come from **LLDP's Management Address TLV**, as real switches send it, instead of a static table. | Joining needs only the VIP and a token. |
| DNS | `LogicalNetwork.dns` (the mgmt network's resolvers, default its `.1`). networkd renders `DNS=` with the static address. | A host on a static address still needs DNS to pull images. |
| Internet in the lab | **Transparent.** The lab's dnsmasq answers every name with the router address. The router relays `:80` (by `Host:`) and `:443` (by TLS SNI) through the lab host's upstream proxy. Guests carry no proxy configuration. | A proxy setting in the guests is a lab-only path (`NO_PROXY` mistakes and so on) that would not exist at home. |
| KubeVirt | **Out of scope.** | It would mean virtualisation inside the guests, which are themselves nested under KVM. |

## 3. The install flow (what a user does)

1. Install Debian 13 on every machine. Cable it to switches whose ports are configured for its template. The mgmt network needs DHCP for new machines, and that pool plus the VIP must be in the mgmt network's reserved range.
2. On the first machine: `curl -fsSL <url>/install.sh | sudo sh -s -- init --vip <vip>`. This installs homelabd, bootstraps a cluster of one and starts it. homelabd moves the machine onto its static address, installs a K3s server with `--cluster-init`, and deploys Longhorn. The script prints the join command.
3. On every other machine: `curl -fsSL <url>/install.sh | sudo sh -s -- join <vip> <token>`. Get the token from `sudo homelabd token` on any member, or from the UI. The machine is approved by its rule, put on its template, and then joins K3s. Control-plane hosts join as servers.
4. `sudo homelabd kubeconfig` on any member prints an admin kubeconfig that points at the VIP (from the control plane's leader, a K3s server, if this host is not one).

## 4. Changes

**model**
- `LogicalNetwork.dns: Vec<Ipv4Addr>`. The seed mgmt network uses `[10.0.0.1]`.
- `LldpNeighbor.mgmt_ip: Option<Ipv4Addr>`.

**control**
- `proto`: `KubeSpec`, `KubeStatus`, `Msg::Kube(KubeSpec)` (leader to agent), `Msg::KubeStatus { host, status }` (agent to the VIP, on change and every 30 s).
- `state`: `ClusterState.kube: Option<KubeCluster { token, init_host }>` and `HostObj.kube: Option<KubeStatus>`. New commands `SetKube` and `RecordKube`.
- `controllers::kube`: computes the desired spec for each `Ready` host and sends it while the host's reported status does not match. It never acts without quorum, like every controller.
- `KubeSpec.storage_network` and `storage_ip`, `KubeStatus.etcd_members`, `etcd_unstarted`, `etcd_unread` and `storage_off` (all `#[serde(default)]`: statuses are in the Raft log), and `Msg::KubeAdmin { remove_etcd_members, etcd_peers, storage_off }`, the work one running server does for the cluster. `controllers::kube::{etcd_removal, join_blocked, storage_network}`.
- `HostOs::apply_kube`, `kube_admin` and `kube_status`. The sim's world makes them a stand-in that is "installed" at once, with an etcd that keeps etcd's rules (a join the members could not take is refused), can stall a join so that a member never starts, and records every change to its members and anything the control plane asked against those rules.
- `ApiOp::GetKubeconfig`: the leader answers with its own K3s server's admin kubeconfig (`HostOs::kubeconfig`), pointed at the VIP. Nothing is written, and the kubeconfig never enters the Raft log or the state clients sync.
- `bootstrap::seeded_durable` takes the K3s token and records the init host.
- The runtime resolves `Addr::Switch` from the LLDP management addresses in the replica's state.

**node (homelabd)**
- `homelabd init | join | token | kubeconfig | run`, plus `install.sh`.
- `LinuxOs` K3s supervisor. It runs on a worker thread and does these steps:
  - prerequisites: `open-iscsi`, `nfs-common`, `iscsid`;
  - the K3s install script and binary of the pinned release, each checked against a pinned sha256 (the script then runs with `INSTALL_K3S_SKIP_DOWNLOAD`), role-specific;
  - the Longhorn manifest on servers;
  - node labels and annotations for Longhorn disks;
  - the storage network attachment config (`/etc/cni/multus/net.d`), and on servers the Multus manifest;
  - status from `k3s kubectl get node`, and on servers etcd's members from `/db/info`;
  - on a server, the cluster work the leader asks for (`KubeAdmin`).
  It reinstalls when the role changes, and before uninstalling a server it deletes its own node so that its etcd member is removed.

**lab**
- Plain-OS cloud-init: hostname, SSH key, NIC names, DHCP on `eth0`, chrony to the router, and the guest agent (the lab's "BMC"). No homelabd and no apt proxy.
- Transparent egress (DNS plus the SNI/Host relay). The root disk grows to 32 GB.
- The technician installs machines over SSH: `init` on `ms01-01`, then `join` with a token from `homelabd token`. *Add VM* does the same.
- `LLDP` frames carry each switch's management address.
- `/api/lab/kubeconfig` asks the control plane for the kubeconfig (`ApiOp::GetKubeconfig`), so it works without the lab too.
- The binary server publishes `homelabd.sha256` beside `homelabd`, and `install.sh` refuses a binary that does not match it.
- The switches count each port's bytes by VLAN (`PortTruth.vlan_rx_bytes`), so the e2e can see where replication runs.

**server and UI**
- The host drawer shows the K3s role and phase and whether the node is Ready. The top bar shows the K3s node count.

**e2e**
- Talks to the Kubernetes API at `https://<vip>:6443` with the admin kubeconfig, using `node:https` (no dependencies).

## 5. Success criteria (added to the lab's §10)

- **K1 Up:** after `./lab.sh up` from a reset lab, every host is a Ready K3s node. The control-plane hosts are etcd servers. Longhorn is deployed and each storage host has a schedulable disk per data disk.
- **K2 Join:** *Add VM* (MS-01) becomes a Ready K3s node with its disks in Longhorn, with no manual step.
- **K3 Volume:** a Deployment with a 2-replica Longhorn PVC writes a token. The volume is healthy, with replicas on two different storage hosts.
- **K4 Host failure:** power off the pod's host. The pod restarts on another host, still reads the token it wrote, and Longhorn rebuilds the lost replica onto another storage host. When the host is powered back on it rejoins as Ready.
- **K5 Leader failover:** power off the homelabd leader, which is also a K3s server. The Kubernetes API answers through the VIP again within the bound, and etcd keeps quorum.
- **K6 Reboot:** reset a K3s server. It comes back Ready with its etcd member intact.
- **K7 Storage network:** Longhorn's `storage-network` setting names the attachment, and every instance manager has an address in the storage network's pod range. A 2-replica volume's engine reaches its replicas at those addresses, and while its pod rewrites 64 MiB blocks, the writer's host sends at least 64 MiB on VLAN 20 in 30 s and at most a quarter of that on VLAN 1.
- **K8 Replace a server:** power off a K3s server that is not the leader and replace it (`ReplaceCpMember`) with a spare MS-01. The spare becomes a Ready K3s server, and etcd, asked directly on a live server, lists exactly the live servers (the voters) while the dead host is still off. Powered back on, the dead host returns as a K3s agent and etcd still lists the voters.

## 6. Phasing

1. Lab realism: plain OS, transparent egress, technician over SSH, `install.sh`, `homelabd init/join/token`, DNS, LLDP management addresses. The existing e2e criteria 1–6 still pass.
2. Control plane: `kube` controller, messages, state, sim stand-in, tests.
3. homelabd: the K3s supervisor and Longhorn.
4. Server, UI and e2e K1–K6, run on the lab, with fixes (K7 and K8 added in §10).
5. README: "Setting up a real cluster".

## 7. Risks

| Risk | Plan |
|---|---|
| The Debian cloud kernel lacks `iscsi_tcp` | Check on the first guest. Fallback: install `linux-image-amd64` instead of the cloud kernel. |
| An SNI relay cannot serve something (an IP literal, a non-443 port) | Find it on the first install. Add a port or a name as needed. |
| K3s or Longhorn is too heavy for the guests | MS-01 guests have 8 vCPU and 16 GB, the mini PC 4 vCPU and 8 GB. Watch memory. |
| The VIP moves to a voter whose K3s is not up yet | Registration retries. In steady state every voter is a K3s server. |

## 9. Findings on the VM lab (2026-10-27)

What running the real install on the VMs found, and what changed because of it:

| Found | Cause | Change |
|---|---|---|
| Every pod was stuck in `ContainerCreating`: the image pull failed with `lookup registry-1.docker.io: Try again`, although `getent hosts` on the same node resolved it. | The lab's dnsmasq answered AAAA queries with REFUSED. glibc tolerates that, but Go's resolver (containerd's) fails the whole lookup. | dnsmasq runs with `--local=/#/`, so other record types get NODATA. A real home router answers AAAA properly. |
| An SSH session that ran `install.sh` would hang. | homelabd moves the machine from its DHCP address to its static one seconds after it starts, and the session's address goes with it. | `init` and `join` return as soon as the service starts. `init` writes the first join token into the new cluster's log, so it can print the join command at once. The guide warns that the session drops. |
| After `install.sh upgrade`, every control-plane host crash-looped and the control plane was down. | A change to `KubePhase` (unit variant to newtype) broke the replay of `RecordKube` entries already in the Raft log. | `KubePhase` kept its shape, plus `KubeStatus.detail` with `#[serde(default)]`, and a regression test replays a first-release entry. **Rule: anything inside a `Command` only gains defaulted fields.** |
| After that crash loop, upgrading did not bring the host back. | systemd had hit its start limit, so the restart did nothing. | `homelabd upgrade` runs `systemctl reset-failed` before restarting. |
| Restarting homelabd (an upgrade, a crash) made K3s crash-loop: flannel panicked in `reCreateVxlan`, every time homelabd started. | On every start, homelabd rewrote its networkd files and ran `networkctl reload`. That reconfigured the interfaces under flannel's VXLAN. This also explained a server that reported `Installing` with no spec while its K3s was down. | `write_network` leaves networkd alone when the files on disk are already the ones it would write. Checked on the lab: upgrading homelabd on all six machines leaves K3s's restart count unchanged. `Installing` now also says what it waits on (`detail`), shown by `homelabd status` and the UI. |
| A new control-plane host was installed as a K3s agent, then reinstalled as a server a second later. | Between the Raft config change that makes a host a voter and the `SetRoles` that gives it the control-plane role, the voters are at target and the host has no role, so it looked like a plain agent. | A host in `cp.voters` is a server even before its role catches up (controller test). On the fresh lab, every host installed once, as the right role. |
| Changing a Longhorn setting failed right after a server rebooted. | Longhorn's admission webhook was briefly unavailable. | The e2e retries. Worth knowing for anyone scripting Longhorn. |

Confirmed as designed:
- Joining servers register through the VIP.
- The Kubernetes API answers through the VIP about 2 s after the homelabd leader (a K3s server) is powered off, because the VIP moves with the leadership.
- A host whose storage VLAN is missing joins Kubernetes and gives Longhorn no disks.
- One full e2e run from a reset lab (`./lab.sh reset`, `./lab.sh up`, then `node e2e/lab.e2e.ts`), with the kubeconfig from the control plane and K3s from the sha256-checked downloads, passes every criterion, K1–K6 included. In that run the K4 pod read its token back 132 s after its host was powered off, and Longhorn rebuilt the lost replica within 174 s.

## 10. The storage network and replacing a server (2026-10-28)

The two real-world gaps of §8 were closed (§2's *Storage network* and *Replacing a dead K3s server* rows, K7 and K8 in §5). Trying both on the lab first found:

| Found | Cause | Change |
|---|---|---|
| A held host, `ms01-05` (racked with VLAN 20 missing), had both data disks in Longhorn, and Longhorn put a new replica there that could not run. | A lab restart had briefly fixed its switch ports, so for a while it stored. Longhorn creates a node's default disks once and never takes them back; the spec's empty `storage_disks` changed nothing. | A running server keeps Longhorn off the disks of every host that does not store (`allowScheduling: false`, noted in `homelab.io/storage-off`) and gives them back once it stores again. |
| `/db/info` through the VIP answers 403. | K3s answers it for the admin only on loopback. etcd's gRPC gateway is not enabled. | Servers read it on loopback for `KubeStatus.etcd_members`. The e2e reads it from a one-off host-network pod on a live server. |
| Deleting a powered-off server's node removed its etcd member within seconds. | K3s's etcd controller holds a finalizer on server nodes (`wrangler.cattle.io/managed-etcd-controller`). | The member is removed by deleting the node, as K3s documents. Never a `Ready` node. |
| rke2-multus alone installs no `NetworkAttachmentDefinition` CRD. | The CRDs (and whereabouts') are in a separate chart, `rke2-multus-crd`. | Both charts go in the manifest. The NAD sits in the same file: K3s's manifest controller retries it until its CRD exists (checked on the lab). |
| After a host was reinstalled from agent to server, its Longhorn instance manager ran without `lhnet1`. | The reinstall wiped K3s's CNI directory, and the kubelet made the pod's sandbox before Multus had written its config again. | Each host deletes its own instance managers that asked for the attachment and run without it (the kubelet's credentials may delete pods bound to their node). Longhorn makes them again, attached. |
| `ms01-05`'s instance manager starts, with an address on VLAN 20 that reaches no one. | Its VLAN 20 interface exists; only its switch ports drop VLAN 20. | Expected: it holds no replicas, and no volume is attached there. A host without a storage interface at all gets no Longhorn (the node selector). |

Confirmed as designed:
- A replacement goes remove-then-add. On the lab, etcd's log on a live server shows the dead member removed at 12:10:17, the new member added at 12:10:38 and promoted at 12:10:45.
- One full e2e run from a reset lab (`./lab.sh reset`, `./lab.sh up`, then `node e2e/lab.e2e.ts`, no criterion rerun) passes every criterion, K1–K8 included:
  - K7: every instance manager has an `lhnet1` address in `10.20.3.0/24`. The engine reaches its replicas at `10.20.3.2:10011` and `10.20.3.0:10000`. In 30 s the writer's host sent 742.2 MiB on VLAN 20 and 0.6 MiB on VLAN 1.
  - K8: the powered-off server was NotReady after 38.1 s. The voters changed 2.0 s after `ReplaceCpMember`. The spare ran a Ready K3s server 64.3 s after the request, and etcd then listed exactly the three live servers while the dead host was still off; its node was gone. Powered back on, the dead host was a K3s agent, every node was Ready 62.6 s later, and etcd still listed the voters.
  - K4: the pod read its token back 106.7 s after its host was powered off, and Longhorn rebuilt the lost replica within 149.1 s, now over VLAN 20. K5: the Kubernetes API answered through the VIP 7.1 s after the leader was powered off.

After review, two gaps in the etcd side were closed (§2's *Replacing a dead K3s server* row). The run above predates them, and they have not been run on the lab yet:
- A dead member K3s cannot find by a node is removed through etcd's gRPC API. That is either a member whose node is already gone or one that never started, which has no name. Before this, the replacement waited for it forever. The request (`Cluster.MemberRemove` over HTTP/2 with curl and K3s's etcd client certificate) was checked against etcd 3.6.5 with client-certificate TLS and no gateway, removing an unstarted learner. The sim covers a replacement that dies while joining and is replaced in turn.
- A server that cannot read `/db/info` used to report no members. That opened the join gate and stopped removals with nothing saying why. It now reports the error, and the controller treats the members as unknown.
